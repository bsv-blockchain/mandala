How a fiat-backed token actually moves

A first-principles walk through issuance, overlay admission, child keys, linkage, sender blinding, and offline settlement — for engineers who know computer science and BSV, and who are willing to learn the cryptography from the group law up.

Companion to the September 2026 whitepaper · github.com/bsv-blockchain/mandala

00 — The one idea

The chain is a notary. The overlay is a court.

Bitcoin SV will mine any transaction whose unlocking scripts evaluate true and whose satoshis have not already been spent. That is all it does. It does not know what a dollar is. It will happily confirm a transaction that mints a million unbacked tokens, pays a sanctioned identity, or spends a frozen coin — as long as the P2PKH unlocks.

Mandala therefore splits labour. Consensus is the notary: it timestamps scripts and prevents satoshi double-spends. The overlay is the court: it decides whether a transaction is a token movement. A transaction may be mined and still be rejected by the overlay. A transaction the overlay accepts is a valid token movement. That is the whole architecture. Everything else is how the court is constrained so that it cannot mint without a public issuance spend, and so that anyone can rerun the same rules.

What miners decide

  • Unlocking scripts evaluate true.
  • Each satoshi is spent at most once.
  • The transaction is in a block (Merkle inclusion).

What the overlay decides

  • Token amounts conserve, except for an authorized Δauth.
  • Every fungible output is bound to an admitted identity.
  • Issuance, freeze, reissue, pause, admit, revoke are threshold-signed.

A licensed issuer is the trust anchor for administrative spends and for the identity graph. Listen-only replicas at exchanges recompute the same predicates and do not mint. Trust is concentrated where a fiat reserve already requires it, and split across keys so that no single officer can mint.

01 — Concentric layers

Four rings, one transaction.

A payment crosses every ring. The holder’s wallet builds a transaction. The overlay checks conservation, linkage, and membership, then signs the txid. Miners confirm the satoshis. The recipient, online or briefly offline, verifies Merkle inclusion and the overlay’s signature. No ring is optional. Skipping the overlay and broadcasting directly produces a mined transaction that is not a token.

02 — The group, from first principles

A private key is a number. A public key is that number of additions of G.

secp256k1 is the elliptic curve Bitcoin uses. The equation is y2 = x3 + 7 over a 256-bit prime field. The points on that curve, plus a point at infinity, form an abelian group under a geometrically defined addition law: the line through two points hits the curve at a third, and you reflect that third point to get the sum. You do not need the geometry to use the protocol. You need three facts.

  1. There is a generator G. Repeated addition of G produces every point in a huge cyclic subgroup. The number of such points is a prime n ≈ 2256.
  2. A private key is a scalar a chosen uniformly from 1 … n−1. The public key is the point A = aG, meaning G added to itself a times. Computing this is cheap (double-and-add). Computing a from A is the elliptic-curve discrete logarithm, assumed infeasible.
  3. Scalar multiplication distributes over addition. (a+b)G = aG + bG, and a(bG) = (ab)G = b(aG). That last identity is elliptic-curve Diffie–Hellman. It is why two people can agree on a secret point without sending private keys.

HASH160, used everywhere Bitcoin puts a key in a locking script, is RIPEMD-160(SHA-256(·)). It is a one-way fingerprint of a compressed public key. Seeing HASH160(P) does not reveal P, let alone the private key.

03 — Shared secrets

Alice and Bob compute the same point. Nobody else can.

Alice holds (a, A = aG). Bob holds (b, B = bG). Alice multiplies her private key by Bob’s public key. Bob multiplies his private key by Alice’s public key.

S = a · B = a · (bG) = (ab)G = b · (aG) = b · A

The point S is a shared secret. An eavesdropper who sees only A and B cannot compute it (computational Diffie–Hellman, which follows from discrete log on this curve). S is the root of every child key Mandala will derive between these two identities. Treat it the way you would treat a master password for the pair (Alice, Bob): never put it on a wire, never give it to the overlay, never write it next to a payment.

In implementations, S is the compressed 33-byte encoding of the point, and that encoding is the HMAC key. The whitepaper writes HMAC(S, ι) for this.

04 — Child keys (BRC-42)

One shared secret, infinitely many one-time keys, selected by an invoice.

BIP32 gives you a tree of keys from one master. BRC-42 gives you a fresh universe of keys per counterparty, because the HMAC key is the ECDH secret with that counterparty. The selector is an invoice number ι.

ι = ℓ-protocolID-keyID

That three-part form is BRC-43. ℓ is a security level (0, 1, or 2) that tells a wallet how loudly to prompt. protocolID namespaces the application (“mandala token”, “mandala admin”). keyID is free-form and, in Mandala, is often the hash of a structured object — so the derived key is a commitment to that object.

k = int( HMAC-SHA256( compress(S), UTF-8(ι) ) ) mod n
H = kG
Pout = B + H = (b + k)G     bout = (b + k) mod n

Read the last line slowly. Adding the point H to Bob’s public key is the same as adding the scalar k to Bob’s private key. Alice can compute Pout because she has a and B. Bob can compute bout because he has b and A. A miner sees only HASH160(Pout). That is a one-time address. Reuse of ι with the same pair would reuse the address; Mandala never does.

Anyone can compute Pout

from (a, B, ι) or (b, A, ι). This is how Alice locks a coin to Bob without asking him for a fresh address.

Only Bob can compute bout

He needs b. That is why the output is his, even though Alice chose the invoice.

The chain sees a fingerprint

HASH160(Pout). Not A, not B, not S, not k, not ι.

05 — The token output

One satoshi, a dropped payload, a standard P2PKH tail.

A Mandala fungible output is deliberately boring. Push the asset identifier and the amount, drop them, then pay a public-key hash. Classification is off-chain: if the script has this exact 8-chunk shape, it is a token. There is no ! prefix. Consensus would ignore it, and the overlay already knows the rule set.

<assetId>  <amount>  OP_2DROP
OP_DUP  OP_HASH160  <h>  OP_EQUALVERIFY  OP_CHECKSIG

assetId is 36 bytes: the genesis outpoint in internal byte order (txid as tx.hash(), then 4-byte little-endian vout). A contract comparing the embedded identifier to an outpoint in the same transaction does not have to reverse anything. The string form remains <txid>.<vout>. Amounts are Bitcoin script numbers in base units. Decimals are metadata, never on-chain. Each output carries one satoshi so the token cannot hide a satoshi balance underneath.

The administrative output is a pay-to-multi-key-hash (minimum two-of-two), optionally prefixed with a JSON blob that is pushed and dropped. The locking keys are themselves BRC-42 children whose keyID is SHA-256(canonical action JSON). Spending the live admin outpoint to produce the next one is the only way to extend the issuance chain. That is the public function of supply.

06 — Two administrative chains

Supply is one spine. Membership is another.

Both chains are hash-linked sequences of threshold spends. Each spend consumes authorized outpoint n and produces n+1. Forging a step requires a live signing threshold. Rewriting history after broadcast requires a deep reorg. Keys rotate by a dedicated spend that publishes the new set, the threshold, and the height h at which it becomes authoritative for fresh attestation signatures.

Issuance — per asset

  • Genesis outpoint is the assetId.
  • A bank deposit is followed by an issue that commits a hash of the deposit record and mints matching face value.
  • Redeem, freeze, reissue are the same chain with a different Δauth.
  • P2MKH, two-of-two minimum; an off-site recovery key is in the set but does not sign day to day.

Registration — per issuer

  • One admission covers every stablecoin that issuer operates.
  • Identity keys are not pushed on-chain.
  • Each spend is admit or revoke. keyID = HASH(event object).
  • A regulator given the event object recomputes ι and the bound key and opens the event.
  • The database is a cache of the replay. It is not the source of truth.

Freeze does not spend the holder’s coin. It marks the outpoint unspendable in overlay state (Δauth = 0). Reissue targets an already-frozen outpoint, evicts it from the overlay’s balance view, and mints replacement units to a named recipient with Δauth = +amount and zero fungible inputs of that asset. Net supply is unchanged in the overlay’s derived view. That conservation is an overlay invariant, not a consensus invariant — by design. A different overlay that admitted the evicted spend would double-count. Do not “fix” this by letting the frozen coin be spent.

07 — Conservation

Outputs equal inputs, plus whatever the issuer just authorized.

Σ aout = Σ ain + Δauth

This is the entire inflation check. A peer transfer has Δauth = 0. An issue has Δauth = +amount, and only because a verified administrative output for that asset is in the same transaction. A redeem has Δauth = −amount, so a partial burn still balances. Try it.

Does the overlay admit this?

100 = 100 + 0. Admitted as a peer transfer.
08 — Linkage: reveal k, never S

The overlay must know who owns an output. It must not learn the master secret.

The association the overlay needs is Pout = B + kG. Two revelations are possible under BRC-69.

Counterparty revelation — S

Anyone with S can recompute HMAC(S, ι′) for every past and future invoice between the two parties. That links their entire history. Mandala never does this for payments.

Specific revelation — k

k is the HMAC output for one invoice. It links one output. Encrypted to the overlay under BRC-72 (BRC-2 encryption to the overlay’s identity key). The overlay checks HASH160(compress(B + kG)) = h and refuses on mismatch.

The same specific revelation is attached to every fungible input. A spend can therefore be named from the identity bound when that coin was first accepted. That is how the overlay knows Alice is spending, even when Bob is shown a blinded key.

Compromise of the overlay’s decryption key discloses the identity graph (who owned which output). It does not disclose S, so it does not let the attacker derive future child keys or decrypt BRC-2 payloads between users. Those use the child-key ECDH, which the overlay never sees.

09 — Sender blinding

Bob must be able to unlock. He must not be able to join Alice’s later payments.

If the remittance carried Alice’s long-term identity A, Bob could derive every future child against A and recognize her. Authenticated BRC-29 payments do exactly that, on purpose, when the payee should know the payer. For a stablecoin moving through the world, Mandala blinds.

r ← {1…n−1}    A′ = A + rG = (a + r)G

Alice presents A′, not A. Bob derives against A′. Consecutive payments sample a fresh r and do not join. This is the same remittance shape as BRC-29 and the same privacy goal as unlinkable payments (BRC-228), with one difference that matters for later proof: A′ is an additive blinding of the long-term identity, not an independent ephemeral. Alice can later open it.

Open

Reveal r. Anyone checks A′ − rG = A. Cheap, and it discloses r, so that particular A′ is now joinable to A. Fine after the fact, when a recipient asks “was this you?”

Schnorr proof of r

Prove knowledge of r such that A′ − A = rG, without revealing r (BRC-94 / RFC 8235). The statement is a discrete log. The overlay never needs this; it already bound Alice from the inputs.

Change outputs locked back to Alice still use A as counterparty. They never leave her wallet, so blinding them would be theatre.

10 — Overlay admission

Sign, withhold broadcast, attach linkage, submit. Broadcast only on admit.

The overlay’s topic manager, tm_mandala, is a pure function of the transaction, the off-chain linkage payload, and derived administrative state. If any gate fails, the transaction is not a token movement. Gates, in order:

  1. Admin-output verification. Re-derive the expected P2MKH (or bound P2PKH) from the canonical action object. Check that the prior authorization outpoint was actually spent. Only the live threshold can extend the chain. register is the first link and has no prior.
  2. Authorized issuance. issue / reissue credit +amount to Δauth. redeem credits −amount. Other kinds credit 0.
  3. Specific linkage. Every fungible output must carry a k that satisfies HASH160(B + kG) = h. Missing linkage is not admitted; conservation then fails; the whole transaction is refused.
  4. Conservation. Per asset, Σ aout = Σ ain + Δauth. This is what stops anyone from fabricating units.
  5. Sanctions. Every identity touching the transaction is screened. A hit refuses the whole transaction, including issuer actions. You cannot reissue to a sanctioned key.
  6. Frozen / evicted inputs. Universal, no admin exemption. The only resolutions are unfreeze or reissue.
  7. Pause. Peer transfers of a paused asset are refused. Verified admin actions still go through, so the issuer can unpause.
  8. Access mode. Denylist or allowlist on the reconstructed registration view, peer transfers only. The issuer’s identity is always authorized.

On admission of T the overlay returns σI under the live issuer key on macc = txid(T). It does not enumerate output indices. If any output in T were not a genuine token, T would not have been signed. Acceptance of the identifier is acceptance of every spendable token output in that transaction. The signature attests to validity at acceptance time, not to the absence of a later spend.

The lookup service ls_mandala is the single writer of derived administrative state. It folds admitted admin actions in chain order (height, offset, a monotonic admit sequence). The topic manager only reads. The database is a cache of that replay.

11 — Offline settlement

The same double-spend window Bitcoin has always had, plus a name the issuer already knows.

Offline mode is a convenience path for short disconnects. Sender blinding still applies. A receiver with cached headers verifies that an offered native input is a mined output by checking a Merkle path. What cannot be known offline is whether that output has already been spent. On reconnect, Arcade — a relay, not an oracle of truth — reports whether the inputs are unspent. The fraud window is the offline interval. The signature already held is evidence.

Token transfers need one extra object: σI on each unique input txid, verified against the issuer key that was live at the height of the corresponding Merkle path, or the current key for unconfirmed inputs. The recipient then has the same existence proof a native transfer has, plus assurance that the issuer accepted those inputs as tokens and already knows who they belong to.

If a fraudulent offline double-spend is alleged, an appropriate authority asks the issuer to open the identity already bound to those inputs. Two offline receivers can both accept spends of the same input; exactly one spend survives contact with the network. That is not a Mandala defect. It is Bitcoin’s offline model, with an identity the overlay already recorded.

12 — What a lying party can and cannot do

State the claims so they can be attacked.

AdversaryCanCannot
A single issuance officer Refuse to sign; stall minting. Mint. The script is at least two-of-two.
A lying overlay Refuse valid transfers (liveness). Create tokens without an issuance-chain spend. Holders mitigate by running a replica and demanding σI at receipt.
Overlay key compromise Decrypt the identity graph. Learn S, so cannot derive future child keys or decrypt user-to-user BRC-2 payloads.
Bob, given only remittances Unlock coins paid to him; see A′. Join Alice’s later payments, or recover A, while r is unopened.
An offline double-spender Hand the same input to two receivers during the disconnect. Have both spends survive reconnect. The issuer can name them to an authority.
A deep reorg The same thing it can do to native satoshis. Forge an administrative step without the live threshold — unless the reorg also erases that spend, which is the same bar as erasing Bitcoin history.

Addresses are single-use. The object that is KYC’d is a long-lived identity key. Compliance is a predicate on that key, not on an address. Legal structure, licensing, and reserve composition are out of scope of the protocol — they are why a licensed issuer exists, not something the script evaluates.
